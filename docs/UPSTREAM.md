# Getting MAS into NumPy or SciPy: what it would take

*Policies checked on 2026-11-13 against numpy/numpy main @ 768d7ef and scipy/scipy main. The engineering measurements come from this machine (i7-1355U, WSL2), using the same harness as [`../study/REPORT.md`](../study/REPORT.md).*

## Short answer

- **Can MAS ship as an experimental NumPy function? No.**
  - NumPy has no `numpy.experimental` namespace and no opt-in flag. Every past experimental mechanism was removed: `numpy.array_api` in 2.0, `NUMPY_EXPERIMENTAL_ARRAY_FUNCTION` in 1.25, and `NPY_PROMOTION_STATE` in 2.2.
  - Polynomials are frozen by NumPy's scope document. It says NumPy will "keep supporting (but not to expand)" this area, and that "maintenance and portability take precedence over performance" (`doc/neps/scope.rst:30,46`).
  - `np.roots` and `poly1d` are documented as legacy. `numpy.polynomial` is pure Python.
- **SciPy is the right venue.** Issue [scipy#5999](https://github.com/scipy/scipy/issues/5999), "Add Aberth–Ehrlich polynomial root-finding", has been open since 2016 with zero comments. SciPy already contains a private `_aberth`, used only for Bessel filters. SciPy's charter covers adding algorithms. NumPy maintainers usually redirect algorithm additions to SciPy (e.g. numpy#11157).
- **Path:** standalone package → GMP-free core → write-up of the method → RFC on the SciPy forum → SciPy PR. For NumPy, at most a "See also" pointer in the documentation, proposed later on numpy-discussion.

## 1. Policies that apply

| topic | NumPy | SciPy |
|---|---|---|
| New feature process | Email numpy-discussion first (`dev/development_workflow.rst:244`). A NEP is for major features; a single function is "an enhancement" but still needs list consensus. | Discuss on the scipy-dev forum first; new features are decided there by consensus (`dev/hacking.rst:40-53`). Line up a reviewer before starting (`core-dev/newfeatures.rst.inc`). |
| Scope | Polynomials: no expansion (`neps/scope.rst`) | Wanted: broadly useful, well understood in the literature, low maintenance |
| Licence | BSD-3. Vendored code is MIT/0BSD/CC0/Apache-2.0+BSD only. No LGPL anywhere; GMP would be unprecedented. | Compatible: BSD-2, MIT, PSF. Incompatible: GPL, Apache. LGPL not listed, but no LGPL dependencies are used in practice. Boost (BSL-1.0) is vendored. |
| Language and build | C++17 allowed (sorting, Highway); Meson | C++17 allowed; Meson |
| CI that must pass | Linux (incl. free-threaded 3.14t), PyPy, Windows (clang-cl x64, **MSVC 32-bit**, ARM64), macOS, armhf, riscv/ppc64le/s390x (QEMU), **Pyodide/wasm**, sanitizers | Comparable matrix |
| PR content | pytest + hypothesis tests, asv benchmark, numpydoc docstring, `.pyi` stubs, `doc/release/upcoming_changes/<PR>.new_function.rst` | Tests, benchmarks, docs |
| **AI policy** | Disclose which tools were used, how, and what code is generated, or the PR is rejected. You must be able to explain all code. Do not use AI to write PR or issue descriptions (`dev/ai_policy.rst`). | Same, plus: "Do not waste developers' time by submitting code that is fully or mostly generated by AI, and doesn't meet our standards" (`dev/conduct/ai_policy.rst`). Copyright of submitted code must be clear. |

**Prior art in the trackers.**
- No Aberth, AMVW, MPSolve or Jenkins-Traub PR has ever been submitted to either project, so none has been rejected.
- Relevant NumPy history:
  - numpy#3555 (open since 2013): use `hseqr` on the Hessenberg companion matrix.
  - numpy#13202 (merged 2019) added a rotated companion matrix to reduce error. numpy#28821 (merged 2025) reverted it, and charris called it a corner case "not to worry about".
  - numpy#14186 pointed to AMVW; nobody followed up.
- A numpy-discussion thread from 2016 about Jenkins-Traub got one reply, which pointed to scipy#5999.

**The AI policy is a substantive issue for MAS.** Most of the 3,100-line C++ port was written with an AI assistant. Before any upstream submission:
- You need to own it: review it, simplify it, and be able to defend every certification step.
- The forum post and PR description must be written by you.
- Disclosure is mandatory.

A standalone package has no such rules.

## 2. Engineering gap (measured)

| # | item | evidence | what to do |
|---|---|---|---|
| 1 | **GMP (LGPL)** in 5 places: exact square-free decomposition (mpq), anchored clusters (mpz Taylor shift), multiprecision fallback (mpf), v1 Sturm path, `certify_sqf` | **515/558** study cases never touch GMP. The other 43: 30 multiple-root cases (exact GCD) and 13 Mignotte cases (anchored). The multiprecision fallback is not reached in the benchmark. | **Stage A:** a GMP-free core (double/double-double paths only). When certification fails, fall back to an uncertified result with a flag. **Stage B:** add exact arithmetic with your own BSD bigint or Boost.Multiprecision `cpp_int`/`cpp_bin_float` (BSL-1.0, header-only). Their speed for this workload is unmeasured. |
| 2 | **Non-portable code** | `__int128`/`u128` (6 uses, modular arithmetic mod 2^61−1), `__builtin_clzll/ctzll` (3), `#pragma omp simd` (9, harmless) | MSVC, 32-bit and wasm need a portable 64×64→128 multiply and bit-scan helpers (C++17, so no `<bit>`). |
| 3 | **Benchmark build is `-march=native`** (AVX2+FMA). NumPy's x86 baseline has no FMA. | Ratio to the native build: x86-64-v3 1.00×; **x86-64-v2 1.5–3.4×** (122 `fma@plt` calls); **x86-64-v2 + Dekker 1.1–1.85×**, bit-identical on 558/558 (`dekker_prod_err.patch`). On v2+Dekker MAS still beats np.roots by 1.4× at n=10, 4.4× at n=80 and 24× at n=1280. | Use the Dekker fallback, and optionally runtime dispatch to an FMA kernel (NumPy has dispatch infrastructure; SciPy mostly doesn't). The Dekker underflow analysis still needs review. **`-ffp-contract=off` is mandatory**, because contraction breaks the error-free transforms (clang contracts by default). |
| 4 | **Unbounded worst-case time** | Coefficients c_k = N(0,1)·1.7^-k: 1.0 s at n=900; **n=2000 had not finished after 300 s.** | Add a precision and time budget with a defined failure mode: return uncertified roots with a flag, or raise. |
| 5 | **API gap vs `np.roots`** | Real float64 coefficients only. `np.roots` also accepts complex input. MAS returns distinct roots plus multiplicities. | **Done:** `certiroot.roots(p)` (highest degree first), `polyroots(c)` (lowest first) and `distinct_roots(p)` (with multiplicities). **To do:** accept complex input (or fall back to eigvals for it). |
| 6 | **Tests must be self-contained** | The current validation uses Arb (python-flint), MPSolve and sympy, which can't be CI dependencies | **Partly done:** `tests/` has oracle-free exact cases (integer, dyadic and √2 roots, multiplicities, threads); the Arb check runs only when python-flint is installed. **To do:** stored references and hypothesis property tests. |
| 7 | **Literature** | SciPy asks whether a method is "well understood in the literature". Aberth is; MAS's correct-rounding certificate is new. | Write a preprint of the method, the proof of the certificate, and the benchmark (`REPORT.md` is most of the evidence). |

## 3. Bugs found and fixed while preparing this study

The edge-case probe found crashes that any library would reject. All are fixed in [`csrc/mas.cpp`](../csrc/mas.cpp):

| bug | symptom | fix |
|---|---|---|
| NaN/inf coefficient | **Process killed (SIGFPE)**: GMP traps in `mpq_set_d` | `solve_impl` returns −2 and the wrapper raises `ValueError` (np.roots raises `LinAlgError`) |
| Exact factor with integer coefficients beyond 2^1024 (e.g. decaying coefficients at n=2000, where the tail underflows to x^k) | **SIGFPE**: `mpz_get_d` → inf → `mpz_class(inf)` in `cpoly_from_q` | Exponent-split conversion through the existing `mpz_to_dd`. The new residual also covers the truncation ulp, which the old bound missed. |
| `round_q` (linear rational factors) | Not strictly correctly rounded: a truncated remainder can land exactly on a midpoint. Also `Q(inf)` → SIGFPE when the root is beyond the double range. | Exact midpoint comparison, overflow threshold DBL_MAX + 2^970, ties to even, and −0.0 kept. **12,012/12,012** cases match Python's correctly rounded `float(Fraction)`. |
| Multiprecision start points | A non-finite or missing approximation would reach `mpf_set_d` (SIGFPE or out-of-bounds read) | Replaced by points on the unit circle |
| Thread safety (ctypes releases the GIL) | `PrecGuard` changes GMP's **process-wide** mpf default precision; `g_exact_evals` was a racy global | Mutex around `solve_factor_mp`; atomic counter. 77 polynomials × 3 rounds on 8 threads: **0 mismatches** vs sequential. The multiprecision path is serialized. |

**Validation after the fixes:**
- Bit-identical to the pre-fix library on all 558 study cases.
- Speed unchanged (new/old 1.00–1.02).
- stress 24/24 + 60/60; sweep 150/150.
- broad3: 5 families × 120, 0 not correctly rounded.
- sqftest 400/0; clus2 clean; imagchk 150/0; migtest 198/0; scalechk 2 × 30/0; bigroot passing.

## 4. Recommended plan (in order)

1. **Ownership and licence.** Decide the licence (BSD-3 to stay compatible with SciPy). Review and simplify the C++ until you can explain every certification step yourself. Remember the AI policies.
2. **Standalone package.** *Started: this repository (setuptools build, pytest suite, CI on Linux and macOS).* Still to do: a meson-python build, cibuildwheel wheels for Linux, macOS and Windows on x64 and arm64, a pytest suite with stored references, asv benchmarks, and numpydoc docstrings. GMP is legally fine here (LGPL with dynamic linking), but going GMP-free early removes the biggest later blocker.
3. **GMP-free core (Stage A)** plus the portability fixes (items 2–5 above). Publish the honest baseline-build numbers.
4. **Preprint** of the method, the certificate and the benchmark.
5. **RFC on the SciPy forum** (discuss.scientific-python.org, scipy category), written by you. Cover the algorithm, guarantees, licence, the benchmark, the maintenance plan and the proposed home (`scipy.optimize`, `scipy.interpolate` or `scipy.signal`). Link scipy#5999 and ask for a named reviewer. A small first step could be to replace SciPy's private `_aberth` in Bessel-filter design. That needs no new public API.
6. **SciPy PR** once there is agreement, with AI disclosure.
7. **NumPy (optional, later):** a numpy-discussion post proposing a "See also" from `np.roots`/`polyroots` to the SciPy function. Do not propose new NumPy API.
